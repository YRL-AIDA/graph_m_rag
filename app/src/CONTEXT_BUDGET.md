# Бюджет контекста в RAG-пайплайне

В этом документе описано, как `app/src/api.py` ограничивает объём контента,
который попадает в промпт LLM (эндпоинт `/ask-document`), и как это настраивается.

## Зачем это нужно

LLM-модель `Qwen/Qwen3-VL-32B-Thinking` (см. `app/config/settings.py`) имеет
большое, но конечное окно контекста. В него одновременно должны поместиться:

1. **Входной контекст** — извлечённые блоки документа + графовое обогащение.
2. **Цепочка рассуждений (thinking / CoT)** — у thinking-модели она может быть
   многотысячной.
3. **Ответ модели**.

Кроме того, это мультимодальная модель: картинки и таблицы кодируются в
**vision-токены**, которые не видны символьному бюджету текста, поэтому их
нужно ограничивать отдельно.

Если не ограничивать контекст, модель может получить слишком длинный промпт
(отказ по `context_length_exceeded`) или потерять качество из-за разбавления
релевантных блоков.

## Ключевая идея

Бюджет делится на две части с разной логикой:

| Источник | Чем ограничивается | Почему |
|----------|--------------------|--------|
| **Первичная выборка Qdrant** (`qdrant`) | количеством блоков (`limit` из запроса, по умолчанию 30) | она уже отранжирована и обрезана по счёту, символьный кап избыточен |
| **Графовое обогащение** (entities, communities, structural, BFS, embedding search) | символьным бюджетом (доля от `MAX_CONTEXT_CHARS`) | эти источники могут разрастаться неограниченно |

Общий жёсткий предохранитель для всех источников — `MAX_CONTEXT_CHARS`.

## Настройки

Настройки находятся в `app/config/settings.py` → класс `ContextBudgetSettings`:

```python
class ContextBudgetSettings(BaseSettings):
    MAX_CONTEXT_CHARS: int = 60000   # общий потолок текста в символах
    MAX_IMAGES: int = 8              # максимум картинок/таблиц (vision-токены)
```

Их можно переопределить через переменные окружения `MAX_CONTEXT_CHARS` и
`MAX_IMAGES` (`.env`), не меняя код.

## Распределение бюджета

Доли графовых источников заданы в `app/src/api.py` в словаре
`_SOURCE_BUDGET_FRAC` (доля от `MAX_CONTEXT_CHARS`):

| Источник | Доля | Бюджет при 60000 симв. | Смысл |
|----------|------|------------------------|-------|
| `qdrant` | — (по счёту блоков) | до ~30 блоков | основная релевантная выборка |
| `entities` | 0.08 | 4800 | сущности, найденные по регионам |
| `communities` | 0.10 | 6000 | отчёты по сообществам |
| `cross_graph` | 0.05 | 3000 | мост между графами |
| `order_neighbors` | 0.04 | 2400 | соседи по порядку чтения |
| `bfs_crawler` | 0.10 | 6000 | обход графа в ширину |
| `embedding_search` | 0.05 | 3000 | поиск по эмбеддингам сущностей/сообществ |

`qdrant` намеренно отсутствует в списке долей: первичная выборка уже ограничена
`limit` (30 блоков), поэтому для неё действует только общий `MAX_CONTEXT_CHARS`.

## Алгоритм (что происходит в `api.py`)

1. **Извлечение** — Qdrant отдаёт кандидатов, reranker/MMR оставляют `limit`
   блоков (`answers`).
2. **Картинки** — к мультимодальному сообщению прикрепляются только первые
   `MAX_IMAGES` картинок/таблиц (по релевантности, т.к. `answers` уже
   отсортированы).
3. **Рендер** — блоки превращаются в строки `context_parts` (XML или flat-формат).
4. **Дедупликация + бюджет** (`# Deduplicate context blocks ...`):
   - заголовки секций, обёртки и закрывающие теги сохраняются всегда;
   - контентные блоки дедуплицируются по первым 120 символам;
   - действует общий кап `MAX_CONTEXT_CHARS` (жёсткий предохранитель);
   - для графовых источников действует их символьная доля; для `qdrant` — нет.
5. Результат присваивается `context_parts` и уходит в `QuestionResponse`
   (поле `context_blocks`).

### Почему раньше блоков было меньше 30

До изменений `qdrant` имел долю `0.30` от `MAX_CONTEXT_CHARS = 18000`, то есть
**5400 символов**. Один крупный блок (например, подпись к таблице на 5 тыс.
символов) исчерпывал весь бюджет Qdrant, и остальные ~29 блоков отбрасывались.
Теперь Qdrant ограничивается только числом блоков (`limit`), поэтому в контекст
попадают все извлечённые блоки, пока не упрётся общий `MAX_CONTEXT_CHARS`.

## Проверка

После изменений для стратегии `reranker` (`limit = 30`) в `context_blocks`
должно быть **30** контентных `<block>` (в XML-формате), плюс структурные
обёртки (`<section>`, `</document_context>` и т.п.). Поле `answers_count` в
результатах теста уже показывало 30 — теперь 30 блоков реально доходят до LLM.

## Рекомендации по подбору

- **`MAX_CONTEXT_CHARS`**: 60000 — консервативное значение (~15–20 тыс. токенов
  смешанного текста), оставляет запас под CoT и ответ. Можно увеличивать, если
  `max_model_len` вашего деплоя подтверждает свободное место, но помните про
  vision-токены картинок.
- **`MAX_IMAGES`**: 8 — разумный баланс «визуальный контекст vs. расход токенов».
  Уменьшайте, если модель падает по длине контекста на «тяжёлых» документах.
- **Доли графовых источников**: меняйте в `_SOURCE_BUDGET_FRAC` (сумма не обязана
  быть 1.0 — это доли от `MAX_CONTEXT_CHARS`, а `qdrant` идёт отдельно по счёту).
